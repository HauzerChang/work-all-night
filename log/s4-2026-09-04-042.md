# S4 chunk 42 — 2026-09-04(拆解真實失敗案例:預設 prompt 寫死人形假設)

## 觸發

使用者用 viewer 的「拆解」分頁對一對機械翅膀(對話貼圖提供,非 repo 既有素材)實測,
反饋「目前使用viewer 進行拆解失敗 甚至跑出完全不相干的人物部件」,並附上 input/output
對照圖。

## 過程

1. 用 chunk 41 建立的技巧(掃 session JSONL 找 base64 image content block 解碼)從對話
   紀錄復原輸入(1536×1024 翅膀)、輸出(1024×1024 人形部件)兩張圖,用 Read 工具確認
   內容:輸入是銀灰+金+紅配色的機械/天使風翅膀,白底;輸出是完全不同主體——黑髮男性角色
   臉部正側面、兜帽披風、胸甲、雙臂護甲、手套、五雙靴子,**沒有任何一個部件跟翅膀有關**。
2. 讀 `s4_ai_viewer.html` 拆解分頁原始碼確診根因:預設 `#decomposePrompt` 文字寫死
   「separate the head, torso, arms, and legs/feet」,明確假設主體是人形角色。使用者
   輸入是翅膀,沒有頭/軀幹/手臂/腿,文字描述與實際圖片直接矛盾。拆解功能刻意用
   `allEditableMaskCanvas()`(alpha全0,整張圖100%可編輯)給模型完全重繪自由,沒有任何
   局部錨定機制——模型在「文字說有人形角色」vs「圖片是翅膀」的矛盾訊號間選擇跟著文字走。
   **明確是預設 prompt 設計疏失(我寫的,只考慮了人形角色情境),不是模型隨機失效**——
   同一 bug 對任何非人形主體(道具/動物/載具等)都會複現,不是翅膀特例。

## 修正

1. **改寫預設 prompt 為主體無關的通用版本**,加入明確錨定語句:
   > "Take the EXACT subject shown in the reference image — do not invent, replace, or
   > substitute it with a different subject or character. ... separate its existing
   > natural parts (whatever they are — e.g. if it has limbs, separate limbs/torso/head;
   > if it is a pair of wings, separate each wing and its feather/segment clusters;
   > if it is an object, separate its natural sub-components)..."

   UI 上加一段提示說明這次修正的背景,並明確提醒**新版本同樣尚未經真實付費呼叫驗證**,
   不要假設改了就一定有效。
2. **順帶修正次要風險**:size 下拉原本固定預設 `1024x1024`,使用者的翅膀輸入是
   1536×1024(寬幅),若沿用預設方形尺寸,畫面會被硬塞進不合比例的正方形畫布、送出前
   可能已變形。新增 `updateDecomposeSizeSuggestion(w, h)`,在 `setMainAsset()` 更新主
   素材時自動依長寬比建議最接近的 size 選項(>1.2→1536x1024;<1/1.2→1024x1536;
   其餘→1024x1024),使用者仍可手動覆蓋。**這不是這次「主體完全被換掉」的主因**,但一併
   修掉降低風險。

## 驗證(Playwright,mock API,未花真實費用)

1. 新 prompt 含 `"EXACT subject"` 錨定語句,不再含舊版 `"head, torso, arms, and legs"`。
2. 三種長寬比合成測試圖(300×100寬幅/100×300直幅/64×64近方形)分別正確觸發自動建議
   `1536x1024`/`1024x1536`/`1024x1024`。
3. 修改後既有拆解流程(mock API 呼叫→顯示結果→用量記錄)仍正常運作,零 JS 錯誤(3 筆
   `ERR_TUNNEL_CONNECTION_FAILED` 是本次測試未 mock ag-psd CDN 的預期網路錯誤,與程式
   邏輯無關)。

## 誠實限制

- 上述驗證只確認「程式碼邏輯照預期運作」,**沒有驗證「新 prompt 真的能讓 gpt-image-2
  忠實重繪翅膀」**——這需要真實付費呼叫才能知道。
- 若重跑後依然主體跑偏,代表問題不只是 prompt 文字,可能是「整張圖可編輯」這個 mask
  設計本身讓 img2img 條件約束太弱,需要考慮換一種送法(但會跟「拆解需要整張重新排版」
  的目標打架,需另外設計)。
- 這是候選17「拆解」子功能第一次遇到真實、嚴重的失敗案例(先前 chunk 35 補圖案例雖 1a
  分數 fail,但視覺上是可辨識的合理延續;這次是主體整個被替換,性質完全不同)。提醒
  「拆解」與「補圖」呼叫模式完全不同(整張圖可編輯 vs 局部mask+大部分原圖保留),可信度
  需獨立評估,不能用補圖那邊的正面結果類推拆解可靠。
