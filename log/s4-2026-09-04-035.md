## 過程

1. **驗證網路解封**:`curl https://api.openai.com/v1/models`(不帶 key)拿到 401(而非之前
   的連線層級 403),確認網路政策確實放行,連線能到達 OpenAI。
2. **驗證 key 授權**:用使用者提供的 key 重測,拿到 200,`gpt-image-2`(及
   `gpt-image-2-2026-04-21` 版本快照、`gpt-image-1.5`、`gpt-image-1-mini`)都在帳號模型
   清單裡。key 全程只在暫存 shell 變數使用,測試後 `unset`,未寫入任何檔案。
3. **建立獨立呼叫模組** `tools/mesh_gen/s4_openai_client.py`——不依賴 Photoshop,純
   `urllib` REST 呼叫(不新增 `requests` 依賴),mask 編碼採 OpenAI 官方慣例
   (alpha 0=可編輯/255=保留),key 只讀環境變數,每次呼叫記錄 metadata(含 API 回傳的真實
   `usage` token 數)到 `tools/mesh_gen/s4_data/openai_usage.jsonl`(不含 key、不含圖片)。
4. **建立用量儀表板** `tools/mesh_gen/s4_usage_dashboard.html`——純前端單檔(比照
   `psd_preview.html` 架構),讀 jsonl 顯示呼叫次數/累積 token/逐筆明細/折線圖。
   `platform.openai.com` 定價頁未放行,查不到官方 $ 定價,故只呈現 token 數,不做 $ 換算。
   只做 `node --check` 語法驗證,**未用 Playwright 完整互動測試**(環境未裝該套件),
   與既有工具的驗證慣例有落差,留意後續補測。
5. **第一次真實測試**:對已知 1a 全 fail 的機械紋理材質(`機器人拆件/左手`)跑
   `punch_hole(interior, frac=0.12, seed=0)` 同一組挖洞參數(與既有 CPU/LaMa baseline
   直接可比),`quality="low"`(最低成本檔位)呼叫一次,用既有 `score()`/`passes()`/
   `score_1b()`/`passes_1b()`(零改動)評分。

## 核心結果

API 呼叫成功(HTTP 200,16.7s,input 1077 tokens/output 196 tokens)。**1a 依然 fail**
(ssim 0.274,同量級於 LaMa 的 0.260,遠低於 0.75 門檻),但**1b 大幅 pass 且是本專案至今
最佳數字**(tone_gap 5.04,遠低於既有機械紋理材質常見的 19~27)。

**⚠️ 關鍵發現**:把 gt/破洞/補丁三張圖並排、4x 放大比對接縫,補丁**視覺上完全看不出破綻**
——材質風格、關節反光、明暗方向全部一致,還自己加了一顆符合機械風格的螺絲細節,跟 CPU
baseline 那種一眼可見的「奶油糊」模糊完全不同等級。但 ssim/premult_mae 依然判定 fail,
原因是 gpt-image-2 生成了一個**風格一致但幾何形狀不同**的合理替代方案(關節弧度/高光位置
跟 gt 不同),不是重建同一組像素。**這代表用逐像素比對 gt 的 1a 評分方法論,對生成式輸出
可能從一開始就是量錯了維度**——生成式模型的本質是「畫一個合理的內容」,不是「重建特定
真值」,兩者在問不同的問題。

**誠實限制(n=1)**:只測一材質一次呼叫(`quality=low`),未做正負對照校準,未測更高
quality 檔位,未套用像素對位管線,未測 edge 模式。這是一個值得跟進的方法論發現,不是
「候選17已驗證有效」的定論。
