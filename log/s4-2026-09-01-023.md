# S4 chunk 23(2026-09-01)——候選16路徑(b):補圖貼回真實 Award spine 場景,動畫截圖比對

## 背景

承接候選 16(見 `knowledge/s4-inpaint-1b-lenient-gate.md`):路徑 (a)「1b 加第4個自我參照
指標」的兩次具體嘗試(chunk 21 候選18、chunk 22 候選20)都已排除,結論路徑 (b)「把補圖結果
貼回真實 `assets/Award.json/atlas/png` spine 場景,在真實動畫時間軸上截圖比對」是唯一未嘗試、
且不依賴發明新自我參照指標的路徑。本次把這條路徑做出來,對一個真實案例完整跑通一次。

## 做了什麼

新增三個工具(`tools/mesh_gen/`,均為新檔案,未改動既有 production 代碼):

1. **`atlas_patch.py`** —— `atlas_crop.py` 的逆操作(extract→貼回)。`rotate=true` region
   用 `cv2.ROTATE_90_COUNTERCLOCKWISE`(`atlas_crop` 還原用 CW 的精確反旋轉)。自我驗證
   `--selftest`:對 `robot_parts` 5 個 region(含 rotate=false/true 兩種幾何)跑
   extract→原封不動貼回→跟原檔整頁逐位元比對,全部 `max_diff=0` PASS。

2. **`s4_spine_render_harness.html`** —— 新的 headless spine-webgl 渲染 harness。不可用既有
   `spine_inspector.html`:其 `TextureAtlas` textureLoader 固定回傳同一張貼圖,對 Award 這種
   雙頁 atlas(`左手`/`頭` 在 `Award.png`,`光暈`/`右手`/`身體` 在 `Award2.png`)會讓其中一頁
   全部貼錯圖。本 harness 的 textureLoader 依 page 檔名字串分派到各自預先載入好的 texture,
   是 spine-webgl `TextureAtlas.load()` 原生支援的用法。新增 `getPoseBounds()`/
   `setCameraFit()` 供跨時間點算相機聯集(見下方踩坑)。

3. **`s4_award_screenshot_compare.py`** —— orchestrator:atlas 解析度切 region → 挖洞(複用
   `inpaint_eval.punch_hole`)→ 1b 盲選補丁(複用 `score_candidates`/`select_best`)→
   `atlas_patch` 貼回一份 `Award.png` 副本 → 組 `orig`/`patched` 兩份完整場景目錄 → 本機
   `http.server` + 產生 Node/Playwright 腳本驅動 harness → 截全場景圖 + 用世界座標換算目標
   slot 的實際螢幕像素框裁小圖比對(不額外放大)+ 存 6x 放大版供人眼複查。

**環境細節**:spine-webgl.js 官方 3.8 build 透過 `raw.githubusercontent.com` 下載到本機快取
(`cdn.jsdelivr.net`/`esotericsoftware.com` 被本容器網路政策擋 403,同候選4/17 已知模式);
Chromium 用 `/opt/pw-browsers/chromium-1194`(node 全域 `playwright` 套件驅動,同
`knowledge/s4-preview-tool.md` 已驗證過的環境設定)。

## 踩到的坑

**相機不能只用 setup pose 框**:第一版沿用 `spine_inspector.html` 的 `fitView()`(只在
`setToSetupPose()` 下算一次骨架包圍盒),對 `Award_Legend_In` 這種爆衝動畫(材質瞬間飛出)
算出明顯不合理的螢幕框(寬度佔畫布 36~40%,某些時間點高度算出負值,代表世界座標超出相機
視野)。**修正**:先用 `orig` 場景跑過全部取樣時間點的 `getPoseBounds()` 取聯集,再固定相機
(`setCameraFit`,15% margin),orig/patched 套同一個框才公平比較。修正後螢幕框穩定在
60~76px 寬、59~64px 高(動畫剛開始 scale timeline 0→1 過渡的極早期幾格框小屬預期)。

## 真實案例:機器人拆件/左手

選材理由:既有 1a fail(機械紋理)/1b pass(接縫不突兀)的代表材質,前面多個候選都用它當
主要測試對象,結論可直接對照;`rotate=false`(降低新工具本身的風險);只在
`Award_Legend_In`/`Award_Legend_Loop`/`Award_Legend_Out` 三支動畫有 attachment timeline。

補洞:atlas 解析度 181×152 裁切 → `punch_hole(interior, frac=0.12, seed=0)` → 洞佔內容
11.3%。1b 盲選:`nearest` 勝出(`pass_1b`,`alpha_gap=0.0, seam_ratio=0.482, tone_gap=0.764`
三項皆 pass,呼應既有 1b 寬鬆閘章節「身體/左手 CPU baseline 在 1b 下全 pass」結論)。

渲染驗證(`Award_Legend_In`×6 + `Award_Legend_Loop`×5,共 11 個時間點):

- **多頁貼圖隔離正確**:全 900×900 場景像素比對 orig vs patched,差異只有 205px,精確落在
  目標 slot 螢幕框內;其他 40+ slots(含同頁的 `頭`、其他頁的 `光暈`/`身體`/`右手`)零差異。
- **實際螢幕佔比**:目標 slot 在全場景截圖裡只佔約 70×60px(≈0.5~0.6% 畫布面積)——這是
  「相機框住整個 LEGEND WIN 爆衝特效」下的真實佔比。
- **MAE(洞區螢幕框內)**:動畫剛開始(scale 0→1 過渡中)為 0;材質完全长开後穩定在
  0.9~1.05(0~255 尺度),量級很小。
- **人眼複查(10x 放大目標區域附近 32×32px 窗格,兩個獨立時間點
  `Award_Legend_In t=0.533`、`Award_Legend_Loop t=0.6`)**:同一個模式——沒有透明殘留、
  沒有色差、沒有硬接縫;唯一看得出的差異是材質中段一道摺痕反光細節在補丁處被抹平一點點
  (呼應候選7「奶油糊」瑕疵),但這個程度在實際渲染尺度下**不構成一眼可見的穿幫**。

## 結論

單一案例(左手)證實:候選7已知的「高頻細節丟失」瑕疵在真實動畫渲染尺度下確實還在,但
**不足以構成視覺上的穿幫**——這是候選16最初想問的問題的第一手直接證據,比候選7的靜態
單層放大代理更貼近實戰。不影響既有 `score_1b`/`THRESH_1B`(本次未改動任何既有 production
代碼,只新增三個新工具)。

## 誠實限制

- 單一材質(左手)、單一 seed(0)、單一 1b 盲選方法(nearest)。`身體` 等其他 1a fail/1b
  pass 材質未驗證。
- 相機框架(骨架包圍盒聯集 + 15% margin)是方法論近似,不確定跟真實遊戲實機顯示的縮放比例
  一致——若實機把特效放更大,目標材質實際佔比會比本次量到的 0.5~0.6% 更大,「不明顯」的
  結論可能不成立,需要真實遊戲畫面比例才能完全確認。
- 人眼複查仍是 Claude vision 自評,非真人標註(同候選7的誠實限制)。
