# 2026-08-28 — S4 session 008(修正 `fill_cv2_inpaint` 的 edge 模式 alpha 處理)

## 這次做了什麼

從 `STATE_S4.md` 下一步候選挑了 #5(`fill_cv2_inpaint` 的 edge 模式 alpha 處理修正)推進。

### 問題回顧

`knowledge/s4-inpaint-evaluator.md` 早在 session 001 就記錄:`edge` 模式(洞跨出輪廓)下,
`cv2_inpaint` 把整個洞區強制設為不透明(alpha=255),但柔和邊緣材質(如光暈放射漸層)的真值
alpha 本應隨半徑衰減 → `alpha_mae` 明顯偏高(28~42)。

### 實驗過程(AC:edge 模式 alpha_mae 應下降,且不能讓任何既有 1a `pass` 判定從 True 翻成 False)

先跑基準:用 `psd_slice.py` 對 `robot_parts.psd`(光暈/身體/左手)重新切件,量出修正前的
edge alpha_mae(41.8 / 4.18 / 5.55),與文件記錄一致。

嘗試三種修正方案,每個都跑同一組 3 件 × interior/edge 全量比對:

1. **對 alpha 通道整顆跑 `cv2.inpaint`**(直覺解法):結果**全面更差**(光暈 41.8→72.5、
   身體 4.18→136.5、左手 5.55→122.6)。原因:Telea/NS 的擴散會把洞外背景的 alpha=0 大範圍
   帶進洞內,連洞中段本該不透明的像素都被拉低。**放棄**。
2. **alpha 單點最近鄰外推**(`fill_nearest` 現成邏輯移過來用):光暈改善(41.8→28.9)但身體
   反而更差(4.18→21.9)。原因:硬邊材質的「最近有效像素」常是緊貼真實輪廓的極薄 AA 邊緣
   像素(alpha 9~30),把洞中段該有的高 alpha 誤判成低。**放棄**。
3. **距離場 × 局部量測漸縮寬度**(`estimate_alpha_taper`,採用):洞外已知背景(alpha≤8)當
   0 端錨點算 `d_bg`;漸縮寬度 `ell` 從洞周圍**看得到的**真實 AA 邊緣像素(8<alpha<250)的
   alpha 梯度中位數量出來(`ell=255/中位梯度`,不是猜的常數,身體/左手量出 ell≈2px、光暈
   量出 ell≈32px,符合材質直覺);`alpha_est=clip(255*d_bg/ell,0,255)`。**三件全面改善**
   (光暈 41.8→8.6、身體 4.18→2.27、左手 5.55→2.98),interior 模式持平(仍 0)。

### 擴大驗證範圍(用 `Symbol_Ww.psd` 4 個新獨立件交叉檢查)

用 `psd_slice.py` 切 `Symbol_Ww.psd`,額外取 4 件(頭/框/臉部陰影/底,涵蓋硬邊/半透明/複雜
拓樸等不同材質)跑同一組回歸,`git stash` 前後比對:

- **edge 模式 alpha_mae 跨全部 7 件一致改善**,無一惡化。
- **1a `pass` 判定翻盤 6 處,全部方向正確**(False→True):光暈 edge、臉部陰影 interior、底
  edge 的 cv2_telea/cv2_ns 從 FAIL 變 PASS;身體/左手/框/頭仍正確 FAIL(RGB 結構本身補不出來,
  與 alpha 無關)。**沒有任何 True→False 的反向翻盤**。
- 唯一的例外:`框`(環形鏤空件)interior 模式 alpha_mae 從 28.5→37.4(數字變差),但 ssim
  本來就遠低於門檻(0.47→0.44),判定沒有翻盤(該材質本身內部有非二值的半透明結構,不符合
  「interior=完全不透明」假設,合成挖洞閘對這種材質本來就不準,屬既有限制而非本次改動造成)。

**曾套用到 `fill_nearest`(Level 1)但 revert**:同一顆 `estimate_alpha_taper` 若也用在
`fill_nearest`,會讓它的 RGB(仍走最近鄰)與新算出的 alpha 來自不同來源像素;實測讓
`框` 的 `ssim` 從 0.775(PASS)掉到 0.452(**FAIL,真實判定翻盤**)。判斷這是因為原本
`fill_nearest` 的 RGB/alpha 同源設計對複雜拓樸有隱性的一致性保護,拆開反而破壞。故 revert,
只把修正套用在候選 #5 明確指名的 `fill_cv2_inpaint`(它的 RGB 本就走獨立的 `cv2.inpaint`
通道,不存在「同源」可保留,沒有這個顧慮)。
