# S4 拆解流程:點提示(point prompt)能否修正 SAM 靜默錯誤?—— 負面結果+一個更有用的發現

> 承接 chunk 47 的兩個改進方向提案,使用者選「1. 加點提示」。本篇記錄實測結果:
> **點提示沒有可靠解決問題**,但過程中意外找到一個更直接、更好處理的真正病因。**沒有
> 修改任何 production 代碼**(唯一的 UI 改動因為驗證失敗已還原,見下方說明)。

## 先驗證再蓋 UI:直接在 Python 層測試點提示效果

在 `s4_decompose_assist.html` 加互動點選 UI 之前,先用已知的 5 個失敗案例(chunk 47:
`bodice`/`sleeve_right`/`hand_right`/`leg_left`/`boot_left`)在 Python 層直接測試
`predictor.predict(box=..., point_coords=..., point_labels=...)` 有沒有效——避免蓋一個
UI 功能結果背後的演算法根本不管用。

### 第一輪:憑印象猜點,失敗(方法論有瑕疵,誠實記錄)

第一次選點沒有先放大看清楚每個框裡實際內容,只憑對圖片的大略印象猜座標。結果 5 個全部
沒有明顯改善或看起來更差。**這一輪的失敗不能拿來下結論**——因為連我自己選的點都可能沒
真的點在目標物件上,這不是在測「點提示有沒有用」,是在測「我猜得準不準」。

### 第二輪:先放大檢查框內容,選精確點,發現更重要的事

用網格疊圖工具把每個問題框放大到看得清座標,**逐一目視確認**要點在哪裡,才發現:

- **`bodice`、`sleeve_right`**:框本身確實包含目標物件(紅色胸衣 / 白紗袖子都在框內
  可見),純粹是 SAM 自動選錯候選——這才是真正適合測試「點提示能不能解決語意歧義」的
  案例。
- **`leg_left`(!)**:框(124,512,212,656)裡**完全沒有腿**——放大看到的是一隻手
  (帶紅色指甲)加上尾巴毛髮材質,跟腿無關。
- **`boot_left`(!)**:框(124,602,225,889)裡**完全沒有靴子**——放大看到的整片都是
  絲帶裝飾布料+尾巴毛髮材質。
- **`hand_right`**:框(345,422,409,512)只有右下角一小塊擦到真正的手腕/手掌,大部分
  框都是白紗袖子——回頭比對原圖更大範圍才找到手的實際位置,發現框本身沒對準。

**這是本次調查最重要的發現**:chunk 47 統計的「5/20 靜默錯誤」裡,`leg_left` 跟
`boot_left` 這兩個根本不是分割演算法的問題——**決策檔裡這兩個框從一開始就沒有正確框住
標籤指定的目標物件**。不管換哪種分割演算法(GrabCut、MobileSAM、甚至完美的人工分割),
框裡沒有腿就不可能切出腿。這個發現比「點提示測試結果」本身更有實際行動價值:**這兩個
案例的正確修法是回到 `s4_decompose_assist.html` 手動重新框,不需要任何演算法改動**。

### 對 bodice / sleeve_right 測點提示:負面結果

對這兩個「框確實正確,純粹分割選錯」的案例,測了兩輪:

1. **只加正向點**(點在目視確認過的目標物件內部):`bodice` 選出的形狀仍然主要是頭髮
   (只是形狀跟純框版本略有不同),`sleeve_right` 選出的內容幾乎跟純框版本一樣,還是
   紅色胸衣——**點幾乎沒有改變結果**。
2. **加正向點+負向點**(在頭髮/胸衣那些一直被誤選的區域額外標負向點):`bodice` 仍然
   主要是頭髮跟白紗混合的錯誤形狀,`sleeve_right` 仍然主要是紅色胸衣+腰帶扣環——**依然
   沒有解決**。

四次嘗試(2部件 × 2種點提示組合)**沒有一次成功修正**,即使點的位置是目視放大確認過的,
不是亂猜。

## 誠實結論

- **點提示在這個案例集上沒有展現出可靠的修正能力**,即使是「框確實正確+目視精確點選+
  正負點組合」這種對點提示最有利的條件下。可能原因(沒有進一步驗證,列出來但不下定論):
  MobileSAM 的 TinyViT encoder 比原版 SAM 的 ViT-H 特徵表達力弱,對點提示的敏感度可能
  本來就比較低;也可能是這批測試案例(半透明材質、大範圍髮絲交疊)對任何 box+point
  prompt 式分割都是結構性困難,不是模型大小的問題。**沒有測試過完整版 SAM(非 Mobile
  版)是否有差異**,這是唯一還沒排除的技術變因。
- **沒有把 `s4_decompose_assist.html` 的點選 UI 蓋出來**——蓋一個沒被驗證有效的功能
  等於在工具裡放一個看起來能用、實際上解決不了問題的假選項,比不蓋更糟。中途已加的
  UI 骨架(按鈕但沒接 JS 邏輯)已經 `git checkout` 還原,repo 裡沒有殘留。
- **`leg_left`/`boot_left` 是決策檔框位置錯誤,不是分割演算法問題**——這個結論比「點
  提示測試」本身更值得優先處理,因為修法是現成的(回到既有的 assist viewer 手動調框),
  不需要新開發、不需要更多演算法投入。

## 對 chunk 47 統計數字的修正

chunk 47 報告「5/20(25%)靜默錯誤」,現在應該更精確地拆解為:

- **2 個是決策檔框位置錯誤**(`leg_left`、`boot_left`)——不是 SAM 的問題,修法是重新
  框選,不需要動演算法。
- **3 個是真正的分割語意歧義**(`bodice`、`sleeve_right`、`hand_right`,其中
  `hand_right` 部分也牽涉框沒對準)——這 3 個目前沒有找到可靠的自動修正方法,點提示
  (含正負點組合)實測沒用。

## 未排除的下一步選項(留給使用者裁決,均未執行)

1. **先修 2 個錯誤框**(`leg_left`/`boot_left`):零成本,回到現有 assist viewer 手動
   調整,不需要任何新代碼。這是目前唯一「已知有效」的改進動作。
2. **對剩下 3 個真正歧義的部件,接受目前自動分割不可靠,改人工處理**:例如在圖像編輯
   軟體手動摳圖,或接受粗略結果留給第4點修補(但已在 chunk 46 討論過,大範圍語意錯誤
   可能不是局部邊緣修補能解決的等級)。
3. **測試完整版 SAM**(非 Mobile 版):模型更大(ViT-H,~2.4GB)、CPU 推論會慢很多,
   換取語意理解力可能更強、對點提示更敏感。這是唯一還沒實驗排除的技術路徑,但成本
   (下載時間、推論時間)明顯更高,值得使用者先確認是否要投入再測試,不像 MobileSAM
   那樣可以先斬後奏。
