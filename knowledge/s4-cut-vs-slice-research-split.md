# S4 研究分流:圖片切割 vs 圖片切片(圖層分解)

> 使用者裁示把「拆解」底下容易被混為一談的兩種動作正式拆成兩個獨立研究區塊。本篇只做
> **範圍界定 + 候選技術掃描**,不是實作規格,也沒有花費任何 API 額度或動任何 production
> 代碼。

## 使用者原話(裁示)

1. **圖片切割**:符合使用者裁切部件(邊緣允許破損)。
2. **圖片切片**(此處可能牽涉到補圖):將單層圖片切成多層——淺層應用:同一部位切出
   「物件層/陰影層/光源層」;深層應用:目標部位帶著遮擋物(例如墨鏡),切出「遮擋物層」
   +「底下被遮住的內容」(例如墨鏡底下的眼睛)。

## 為什麼要分開:兩者本質不同,不能用同一套方法

- **切割是空間切分**:一張圖裡本來就有多個部件並排/前後疊放,只是原始檔案沒拆開存,
  用幾何裁切(+局部修邊)就能還原成多個獨立圖層——**原始像素資訊都還在**,不需要
  「無中生有」。這正是六階段拆解流程(`s4-decompose-restage-plan.md`)的第3點,已有
  明確技術路徑(part list 決策檔 → 幾何裁切 → ag-psd 組回 PSD,已驗證),**不需要另開
  新研究**。
- **切片是訊號分離/反推**:同一像素位置疊了多種效果(打底色+陰影+高光,或遮擋物蓋住
  底下內容),要把疊在一起的東西拆開。這不是幾何問題,是「反推生成過程」的問題,而且
  難度依「底下內容是否還留在畫面裡」分成完全不同等級:
  - **淺層(陰影/光源分離)**:底下的資訊理論上都還在——陰影只是把顏色壓暗/疊色,
    沒有真的遮住任何形狀,像素還是同一批像素,只是被混合了。屬於**訊號分解**,有機會
    用傳統影像處理(反推 blend mode 數學)做到,不一定要生成式模型。
  - **深層(遮擋物底下的內容,如墨鏡下的眼睛)**:底下內容**在畫面上完全不存在**
    (像素被遮擋物完全蓋住,根本沒被記錄下來)。不管用什麼傳統方法都生不出「原本沒有
    記錄」的資訊,本質上一定要生成式模型「腦補」——這跟拆解流程裡「情境2視角外推」
    (CLAUDE.md「反推框架」提過的難題分類)是同一等級,只是觸發條件不同(這裡是被
    物件遮擋,不是被視角遮擋)。

## 區塊 1:圖片切割 —— 沿用既有六階段第3點,不需另開新研究

**AC(驗收標準)**:依決策檔(`bbox_px`)裁出的每個部件形狀正確,**允許裁切邊緣像素
破損/羽化不完美**——因為後續有第4點 GPT 局部修補收尾,不需要切割這一步就做到完美邊緣。

這個「邊緣允許破損」的裁示,正式確認了 chunk 43 log 裡已經提到但沒明講的假設(「GPT
局部修補的 mask 設計,呼應 8px 融合邊界慣例」)——現在有使用者明確授權,第3點的裁切
實作可以用最簡單的硬邊界矩形/多邊形裁切,不需要為了追求完美邊緣做額外的羽化/抗鋸齒
運算,把這些工作留給第4點的局部 mask 修補處理更划算(用生成模型直接把邊緣「畫順」,
比用傳統演算法猜怎麼羽化更可靠)。

**下一步**:第3點(讀決策檔→裁切→組回PSD)可以直接開工,技術路徑已在 chunk 44 驗證
(ag-psd `writePsd` 讀寫皆可用)。

## 區塊 2:圖片切片(圖層分解)—— 新研究主題

### 2a. 淺層應用:同部位切出「物件/陰影/光源」層

**候選技術方向(CPU-first,不需要生成式模型)**:

- **前提假設**:美術風格是「平塗+疊色塊」式上色(常見於手遊/slot 遊戲角色立繪),
  陰影跟高光是用 multiply/screen(或 add)疊在底色上的色塊,不是連續漸層厚塗。若是
  厚塗渲染風格,這個假設不成立,整條路徑需要重新評估。
- **構想步驟**(尚未實作,純研究筆記):
  1. 對部件圖做顏色量化/分群(如色相-飽和度 k-means,或平滑區域 flood-fill),找出
     「面積最大、最可能是打底色」的區域當基準色。
  2. 對每個像素,比較它跟所屬分群基準色的關係:亮度顯著降低、色相相近 → 疑似陰影
     (multiply 疊色);亮度顯著提高,或偏白/偏冷色 → 疑似高光/光源(screen/add 疊色)。
  3. 用對應 blend mode 的反函數,從「合成後像素」+「基準色」反推陰影/高光層本身的
     顏色與 alpha(multiply 反推:`shadow_alpha ≈ 1 - L_composite/L_base`;screen
     同理反推)。
  4. 輸出 3 張獨立圖層(物件基色層 + 陰影層 + 光源層,各自帶 alpha),供 spine 各自
     掛 slot,之後可獨立做位移/淡入淡出做出「光源移動」的效果。
- **可行性評估**:中等信心。反推 blend mode 數學本身是成熟技術(圖層疊色公式是公開
  已知的),真正風險在「基準色分群」這一步——若美術風格是漸層厚塗、或陰影/高光形狀
  本身很複雜(非簡單色塊),分群會失敗,結果會是雜訊而不是乾淨的三層。**這需要先用
  真實素材做一次可行性驗證才能判斷,本次尚未做**。
- **與既有 GenieLabs 知識的關係**:無直接關聯(chunk 38 萃取的是部件版面重繪+SIFT
  自動定位,是不同問題)。

### 2b. 深層應用:遮擋物 + 被遮擋內容 分離(如墨鏡下的眼睛)

**問題本質**:這不是「分解」,是「補全」——底下的眼睛像素在原圖裡不存在,只能靠生成
模型根據上下文(臉型/另一隻沒被遮的眼睛/角色設定)推測合理內容。

**技術路徑(初步掃描,不是規格)**:

1. **遮擋物本身的分離**(墨鏡形狀,含鏡框+鏡片):這一半屬於區塊1的「切割」問題——
   墨鏡在畫面上是完整可見的物件,用語意分析(Claude vision,比照六階段拆解第1/2點)
   +使用者框選確認邊界,就能單獨拆出「墨鏡層」,不需要生成模型。
2. **底下被遮住的內容**(眼睛):必須用生成式 inpainting——把墨鏡形狀當 mask(alpha=0
   的可編輯區),讓模型在「已知是一張臉、已知遮擋物形狀、已知另一側五官」的上下文下
   補完。這跟既有 candidate 17(gpt-image-2 masked edit)技術上是同一個 API 呼叫模式,
   但**用途完全不同**:candidate 17 目前驗證過的場景是「填補裁切造成的邊緣缺口」
   (缺口小,周圍上下文直接告訴模型該長什麼樣);這裡的 mask 是「整個遮擋物的完整
   footprint」(缺口可能不小,需要模型做更多語意推理,不是單純延伸鄰近像素)。**不能
   直接沿用 candidate 17 已驗證的可靠度結論,需要獨立測試**。
3. prompt 設計需要明確告知「這裡原本應該是什麼」(如「移除墨鏡,補上這個角色風格一致
   的眼睛,可參考另一側沒被遮擋的五官比例」),避免重蹈 chunk 42 翅膀案例的錯——不能
   讓模型自由發揮到偏離角色本身。

**可行性評估**:低-中信心,且**必然要花真實 API 費用**才能驗證(CPU-only 方法本質上
做不到)。建議真的要投入前,先確認這個需求在目前的 spine 動畫規格裡有沒有實際案例
(手上有沒有真的需要「拆遮擋物+補底下內容」的素材?),避免研究資源投在假設性需求上。

## 誠實限制

- 本篇是研究筆記+方向掃描,**不是可執行的實作規格**。2a 的 blend-mode 反推構想沒有
  經過任何真實素材測試,可行性是推論不是已驗證結論。
- 沒有花費任何 API 額度,也沒有動任何 production 代碼。
- 2b 深層應用目前沒有比「用既有 GPT masked-edit 能力,換一個更貼切的 prompt/mask
  策略」更具體的技術路線,而且結論仍待真實付費測試才能確認,跟 candidate 17 已驗證的
  「局部邊緣修補」用途不能直接類推。
