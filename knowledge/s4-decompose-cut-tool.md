# S4 拆解流程第3點:實際裁切工具 + PSD 組裝(區塊1正式落地)

> 承接使用者裁示「排程上優先研究區塊一(圖片切割),達到一定技術水準後再進區塊二」。
> 這篇記錄第3點(讀決策檔→實際幾何裁切→組回PSD)的實作,不只是研究筆記——這次有真正
> 落地的 production 代碼,且做了會失敗的自我驗證(不是隨便跑過就宣稱成功)。

## 產出

1. **`tools/mesh_gen/s4_decompose_cut.py`**:讀來源扁平圖 + `s4_decompose_assist.html`
   匯出的決策檔(`bbox_px`)→ 對每個部件做硬邊界矩形裁切 → 輸出各部件 PNG + 跟
   `psd_slice.py` 相容的 `manifest.json`(`s4-psd-contract.md` 定義的格式)。
2. **`tools/mesh_gen/psd_node/`**:獨立 Node 子套件(`ag-psd` + `pngjs`,無 native
   build 依賴——`node-canvas` 在這個環境裝不起來,缺 `pangocairo`,改查 ag-psd 型別定義
   發現 `Layer.imageData` 直接吃 `{data,width,height}` 純像素陣列,不需要真的 Canvas
   物件,換 `pngjs` 純 JS 解 PNG 就夠)。`manifest_to_psd.js`:讀 `manifest.json` + 部件
   PNG 目錄 → 用 `ag-psd` 的 `writePsd()` 組成多圖層 `.psd`。

## 用法

```bash
# 第1步:裁切(讀決策檔,輸出各部件PNG+manifest.json)
python3 tools/mesh_gen/s4_decompose_cut.py <來源.png> <決策檔.json> -o <輸出目錄> --eval

# 第2步:組回PSD(讀manifest.json,輸出.psd)
cd tools/mesh_gen/psd_node && npm install   # 只需第一次
node manifest_to_psd.js <輸出目錄>/manifest.json <輸出目錄> <目標.psd>
```

## 設計:硬邊界矩形裁切,零羽化(呼應區塊1 AC)

單純空間切分,不做任何邊緣柔化/去 bleed 嘗試——每個部件就是來源扁平圖上的一個矩形窗口,
窗口內容原封不動裁出來。這代表**部件邊界一定會夾帶鄰近部件的內容**(例如「上半身胸衣」
的裁切框內,邊角可能包含一點袖子或頭髮的像素),這是使用者已經明確授權的「邊緣允許
破損」——邊緣品質不是這一步的責任,留給第4點 GPT 局部修補去清理。

## 自我驗證閘(AC1/AC2/AC3)——含兩次失敗,誠實記錄診斷過程

第一版直接照搬 `psd_slice.py` 的重組驗證邏輯(threshold 完全相同),拿 chunk 41 的
九尾焰蓮測試素材(真實跑過 `s4_decompose_assist.html` 匯出的決策檔,20個部件,不是我
手造的假資料)實測,**兩項都不過**:

```
AC2_reconstruction: premult_rgb_mae=13.06, alpha_mae=61.65 (thresh 2.0) FAIL
AC3_no_orphan:      orphan_ratio=0.242 (thresh 0.005)                    FAIL
```

沒有直接調高 threshold 蒙混過關,而是先畫圖確認孤兒像素分布在哪裡(用洋紅色疊圖標示
`cover==0` 但來源圖 alpha>8 的像素)。**根因找到**:九尾焰蓮的測試素材
(`jiuwei_yanlian_char_crop.png`)是從角色設定資料表**直接矩形裁下來的一塊面板**,不是
去背後的獨立角色——整張圖 `mode=RGB`,**完全沒有 alpha 通道**(轉 RGBA 後全部
`alpha=255`)。孤兒檢查用「alpha>8 = 有內容」判斷角色範圍,對這種來源等於把整張畫布
(含背景、標題文字)都當「角色內容」,任何沒被部件框蓋到的背景/文字自然被誤判成
「漏掉的部件」——**不是裁切工具的邏輯錯,是拿去背判準套在沒去背的圖上,方法論不匹配**。

### 驗證修法本身有效:對真正有 alpha 的來源跑回歸測試

不是靠推論就結案,而是找一個**真的有乾淨去背 alpha 的既有資產**
(`assets/robot_parts.psd`,經 `psd_slice.py` 讀出的原始 leaf 圖層座標當 ground
truth)反向構造決策檔:

- 用 `psd_slice.py` 已知正確的 5 個部件 offset/size 直接組成 `bbox_px` 決策檔餵給
  `s4_decompose_cut.py` → **AC3 孤兒率 0.0,精確通過**,證實孤兒檢查邏輯本身沒問題,
  問題只出在九尾焰蓮那張圖沒有 alpha。
- AC2 重組 MAE 落在 2.06(原 threshold 2.0,壓線未過)——追根究柢,差異全部集中在
  部件邊界的半透明/抗鋸齒像素(premultiplied diff>20 的像素只佔 4.9%,且分布在邊界),
  不是整體性錯誤。這正是矩形窗口重組固有的邊緣代價(見下段解釋),跟「邊緣允許破損」
  是同一件事,不該用 psd_slice.py 那種「真正獨立圖層」的高精度 threshold 去卡。

### 兩次負對照(negative control):確認孤兒檢查真的抓得到漏部件,也誠實記錄它的盲點

1. 刻意從 robot_parts 決策檔拿掉「身體」部件重跑 → **孤兒率仍是 0.0,沒被抓到**。
   診斷:「光暈」部件的 bbox `[6,10,712,693]` 幾乎蓋滿整張畫布,把「身體」的區域也
   幾何涵蓋進去——因為裁切來源是同一張**已經合成過的扁平圖**,「光暈」的裁切框內本來
   就含有身體的像素(不是真的光暈圖層本身的獨立內容,是合成後那個位置剛好長那樣)。
   **這是這個工具的真實限制,不是誤判**:孤兒檢查只能抓「幾何座標完全沒被任何框蓋到」
   的漏洞,抓不到「語意上少了一個部件,但剛好被另一個框的矩形範圍幾何涵蓋住」的情況。
2. 改成拿掉「光暈」(涵蓋全圖、其他4個部件無法涵蓋的部件)→ **孤兒率 4.18%,正確判定
   fail**。證實孤兒檢查對「真的沒被任何框蓋到的區域」是有效的,只是對上述第1種情況
   是盲點。

### 最終版驗收邏輯(已修正,誠實反映每一項的真實保證等級)

- **AC1(部件數>0)**:硬性,失敗就是真的沒東西。
- **AC2(重組落差)**:改成只回報數字,**不再擋 overall_pass**——矩形窗口在鄰接部件的
  柔邊/半透明邊界必然會有一點落差,這是設計本身接受的代價,不是缺陷。
- **AC3(孤兒檢查)**:先判斷來源圖是否「幾乎整張 alpha=255」(≥99% 像素),是的話
  自動跳過並在報告裡說明原因(不誤判成失敗);只有在來源圖有意義的 alpha 時才真的拿
  來當硬性檢查。使用者若要對「矩形面板裁圖」這類無 alpha 素材做完整覆蓋率驗證,目前
  沒有自動化手段,需要人工確認決策檔涵蓋了整個角色。

## 端到端管線驗證(真實資料,非合成測試)

用 `s4_decompose_assist.html` 對 `jiuwei_yanlian_char_crop.png` 實際跑過(載入圖+載入
chunk 43 產出的建議 JSON+匯出,零人工修改)產生的**真實決策檔**(20個部件),完整跑過
`s4_decompose_cut.py`→`manifest_to_psd.js`:

- 裁切:20 個部件 PNG 全部產出,`head` 部件逐像素比對來源圖對應區域**完全相同**
  (`ImageChops.difference` 空 bbox)。
- PSD 組裝:`manifest_to_psd.js` 成功寫出 460×898、20 圖層的 `.psd`。
- **獨立交叉驗證**(跟 chunk 44 一樣的方法論,用不同套函式庫互相驗證):Python
  `psd-tools`(跟寫入用的 `ag-psd` 完全不同套件)重新讀取這份 `.psd`——圖層數量、
  每層名稱、每層 offset/size 全部跟 manifest 精確相符;抽樣一層(頭部)逐像素比對
  PSD 內容跟原始裁切 PNG **完全一致**。

## 誠實限制

- 硬邊界矩形裁切**沒有**去除鄰近部件的 bleed,是刻意設計(使用者授權),不是疏漏。
- 決策檔格式沒有 z-order(疊放順序)欄位——`s4_decompose_assist.html` 目前只讓使用者
  框選範圍,不記錄前後遮擋順序。本工具預設用決策檔 `parts` 陣列的出現順序當 z(index
  越大越上層)。對這次測試素材(矩形窗口內容彼此像素相同,順序其實不影響重組結果)
  沒有實際影響,但**如果未來有部件之間有真正衝突的視覺內容需要指定疊放順序**,現有
  格式無法表達,需要另外擴充(可能是 assist viewer 加拖曳排序功能)。
- AC3 孤兒檢查有上述記錄的兩個盲點:(1) 對無 alpha 的扁平面板圖完全失效,已知並自動
  跳過;(2) 對「被另一個大範圍框幾何涵蓋住」的漏部件檢測不到,目前沒有解法(需要語意
  層級的判斷,不是純幾何能解決的問題)。
- 只驗證過本次的兩份真實素材(九尾焰蓮 20部件、robot_parts 5部件的正/負對照),沒有
  對更多樣的美術風格/部件數量做壓力測試。
- 第4點(GPT 局部修補收邊緣)仍未開始——這次只把第3點做完並验證清楚。

## 使用者親自確認的真實決策檔測試(比自動示範更重要的一次驗證)

以上驗證都是用 chunk 43 我自己視覺估計產生的草稿決策檔。使用者接著親自打開
`s4_decompose_assist.html`,對草稿框做了真實調整(對照可見:`fox_ears` 從
`[138,0,345,72]` 調整成 `[182,12,383,105]`、`leg_right`、`sleeve_left`、
`tails_mass`(改成 `[9,284,449,895]`,幾乎橫跨全寬)都不同於草稿),匯出決策檔後直接
餵給我跑,並要求「讓我看看切完之後的成果」——這是六階段設計裡「使用者做最終邊界決策」
這一步第一次真實發生,不是我方模擬。

用這份真實決策檔重跑:20 部件全數產出,AC1/AC3 pass(AC3 因來源圖無 alpha 依規則
skip),AC2 資訊性 MAE 4.41(比草稿版的情況更低,推測是使用者調整後的框更精準)。

**視覺檢視每個裁出來的部件(montage 逐格檢視,不只看聚合指標)後,誠實結論**:矩形裁切
的 bleed 問題比「邊緣有一點破損」嚴重不少,好幾個部件的裁切框內容**主體不是它自己標籤
宣稱的東西**,而是被鄰近內容佔滿:

- `head` 框裡有一大截標題文字(「JIUWEI・YANLIAN」)+ 部分狐耳,頭部本體只佔小半。
- `earrings` 框幾乎整個是臉,耳環本身極小一塊。
- `choker` 框主要是裸露肩膀/鎖骨,頸飾本身占比很小。
- `sash_train` 跟 `tails_mass` 兩框大範圍互相重疊(這是低信心欄位本來就標注過的已知
  問題),裁出來的內容高度相似,不是兩個清楚分開的部件。

這跟之前用 robot_parts 驗證的「小幅邊緣落差」是不同量級的問題——robot_parts 的部件
形狀本身接近方形/緊貼 bbox(機械部件),矩形窗口浪費的面積小;九尾焰蓮這種**有機、
不規則、大範圍疊放**的角色插畫,bbox 天生就會框進大量不相關內容,不是「邊緣」層級的
瑕疵,是「這個框選到的東西有一半不是它」的量級。**這已經超出使用者原本授權的「邊緣
允許破損」的範疇**,單靠第4點的局部邊緣修補(小範圍 mask)很可能不足以清理——像
`head` 這種框,需要修補的不是邊緣一圈,是整塊標題文字區域,這比「補邊緣」更接近
「大範圍重繪」,反而更靠近使用者已經因為翅膀案例(chunk 42)否決掉的做法。

**這是需要回報使用者裁決的真實發現,不是可以自己決定忽略的細節**:對這種高複雜度、
部件形狀不規則、大範圍前後遮擋的角色素材,純矩形 bbox 裁切可能從根本上不夠用,需要
考慮:(a) 接受目前結果,靠加大第4點修補範圍硬做;(b) 升級 assist viewer 支援不規則
多邊形/筆刷選取(不再限於矩形),裁切階段跟著改用該形狀當 mask 而非矩形窗口;
(c) 認清這類角色屬於「高複雜度人物」課題(CLAUDE.md 已定調的獨立難題),用比機器人
拆件更寬鬆的品質標準看待,分階段处理(先接受粗略部件,細節留給後續 spine 階段手動修)。
本次沒有替使用者做這個決定。
